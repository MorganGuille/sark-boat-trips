# CLAUDE.md

Sark Boat Trips: booking site and owner dashboard for a small boat-trip business. MERN stack (React 19 + Vite client, Express 4 + Mongoose server, MongoDB Atlas, Stripe for charters, Gmail SMTP for email). Single owner uses the dashboard. This repo is the **sandbox** (`version2` branch, sandbox DB `Bookings-Sandbox`); production is the Heroku app from `main`.

The backlog is in `spec.md`. Update it when an item is done or a new problem turns up.

## Run, lint, build

- Dependencies: server deps are in the **root** `package.json` (no `server/package.json`); client deps in `client/package.json`.
- **Local site:** two terminals, both from the project root: `npm run dev:server` (the API on 4040, restarts itself when a server file changes, uses Node's built-in `--watch` so `nodemon` isn't needed) and `npm run dev:client` (the website on 5173). Open `http://127.0.0.1:5173`.
- **Server:** `cd server && node index.js` (default port 4040). dotenv reads `.env` from the *current directory*, so it must be started from `server/`. Heroku runs `node server/index.js` with config vars instead. No auto-reload: restart after server changes.
- **Client:** `cd client && npm run dev` (Vite, port 5173).
- **API URL:** nothing is hand-edited. `client/config.js` reads `VITE_API_URL`: `npm run dev` gets the local server from the committed `client/.env.development`, and a production build leaves it empty, so the browser calls the same site that served the page (the Express server serves both). Restart `npm run dev` after changing that file.
- **Lint:** `npm run lint` from the root (website code only). It must show 0 errors; the 7 warnings are fine. Build output (`dist`, `dist-server`) is ignored, and the project doesn't use PropTypes, so that rule is off.
- **All checks:** `npm run check` (lint, server tests, browser tests). See "Tests and checks".
- **Build:** `npm run build` rewrites the *tracked* `client/dist` and `dist-server`. Don't run it in place. For a build check use `npx vite build --outDir <scratch dir>`. If dist gets modified by accident, `git checkout -- client/dist` and delete the new hashed files.
- Never print `.env` values. `server/.env.example` lists every setting with comments. The names are: `PORT, admin_username, admin_password_hash, JWT_SECRET, atlasDB_name, atlasDB_user, atlasDB_user_password, atlasDB_password, gmail_address, gmail_password`, plus the Stripe and address settings: `PUBLIC_URL` (the site's public address, e.g. `http://localhost:5173` on a laptop and `https://www.sarkboattrips.com` in production; Stripe sends customers back to it and owner emails link to its `/dashboard`), `STRIPEKEY` (live; production only), `STRIPETESTKEY` (test; used everywhere that isn't production), `PRICE_ID` (the charter deposit price; test and live modes have different ones), `STRIPE_WEBHOOK_SECRET` (the `whsec_...` of that environment's webhook; without it `/charters/webhook` returns 503 and `/success` still creates the booking), optional `TRUST_PROXY` (number of proxies in front of the app, default 1), and an unused `DB_*` Postgres block. **Charter payments only run when `utils/settings.js` is satisfied**: outside production only a test key is used (a live key with no test key switches payments off, so a laptop can never charge a real card), and a missing or invalid `PUBLIC_URL` or `PRICE_ID` switches them off with a clear message at startup and a 503 to customers. Never type an address, price or key choice into the code: add a setting. The server exits at startup if `JWT_SECRET`, `admin_username` or `admin_password_hash` is missing. **Database:** `utils/database.js` builds the Atlas address (`atlasDB_user` + `atlasDB_user_password`, falling back to the original user `morganguille` + `atlasDB_password` until production has its own user). Outside production the server and the scripts refuse any `atlasDB_name` without "sandbox" in it; `MONGODB_URI` is the deliberate override. One Atlas cluster holds the sandbox database `Bookings-Sandbox` and the live site's `Test`; never touch `Test`.

## Layout

- `server/app.js`: the Express app (middleware and routes). Order matters: security headers, HTTPS redirect (production only), Stripe webhook (raw body, before `express.json()`), JSON, CORS, static `client/dist` (or `CLIENT_DIST`), routes, catch-all to `index.html`, error handler. `server/index.js`: reads `.env` first, checks the login settings, connects to MongoDB (`MONGODB_URI` overrides the Atlas address) and listens.
- `server/test/` (server tests and their helpers), `e2e/` (browser tests), `.github/workflows/ci.yml` (CI).
- `server/routes|controllers|models|middleware`: `bookings`, `admin` (login, season dates), `charters` (Stripe), `notes`. `middleware/requireAuth.js` checks the JWT. `scripts/hash-password.js` makes the bcrypt hash for `admin_password_hash`.
- `client/src/views` (pages), `components` (shared), `components/dashboard` (dashboard pieces), `hooks/useSeasonDates.js`, `services.jsx/` (API helpers, `auth.jsx` holds the token and `authAxios`), `utils/dates.js`, `css/`.

## Data and rules to remember

- **Dates** are `YYYY-MM-DD` text (for example `2027-05-01`) in bookings, availability and notes, in the database and over the API (season dates too: stored as UTC midnight, sent as `YYYY-MM-DD`). That form sorts and compares correctly as plain text, so "from today" and "this month" are simple searches, and it has no time zone. **People read it day-month-year (`dd-mm-yyyy`), so convert only where a person reads it:** `showDay` in `server/utils/dates.js` for emails and messages, and `showDay`/`prettyDate` in `client/src/utils/dates.js` for screens. `dayNumber`/`isDay` (server) check a value is a real `YYYY-MM-DD` day, and every route that takes a date refuses anything else (including the old `dd-mm-yyyy`). Never write a date into an email or message without `showDay`. The edit form uses `<input type="date">`, which gives `YYYY-MM-DD` and shows the visitor's own format.
- **Collections:** the model named `Admin` is the `admins` collection and holds the single season-dates document. Don't rename it: production uses it. Model `bookings` is the `bookings` collection.
- **Timeslots** are `'11am'` and `'2pm'`. Default capacity is 12. All seat counting lives in `server/utils/availability.js`: seats left = capacity minus (adults + children) of non-cancelled bookings, or 0 if the trip has an active charter. `isSlotEmpty` (open and no bookings at all) is the rule for booking a charter. Don't copy this logic elsewhere.
- **Cancel, not delete:** bookings have `status` (`active` or `cancelled`) and `cancelledAt`. A booking with no `status` counts as active. Day view and search hide cancelled bookings unless `?includeCancelled=true`. Permanent delete only works on cancelled bookings.
- **Validation lives in `utils/validateBooking.js`:** `validatePublicBooking` (async; customer bookings and charter checkout: required fields, email, lengths, party size 1-12 adults and 0-12 children, trip time, real date, not past, 1 hour cutoff in `Europe/Guernsey` time, inside the season), `validateAdminBooking` (dashboard add and edit: lenient, only checks what is given, past dates allowed) and `validateAvailabilitySetting`. The trip times (`11am`, `2pm`), the 12 limit and the cutoff are constants at the top of that file. Never compare dates as strings: use `dayNumber`. Values must be real strings or numbers, never lists or objects.
- **Editing a booking** (`updateBooking`): a field that isn't sent is untouched, an empty text field clears it, date, trip time and booking type are never blanked, a blank adults box leaves the number alone and a blank children box means 0. It saves through the document with `validateBeforeSave: false` (the validators in `validateBooking.js` run first), refuses if the new date, trip or party size doesn't fit (`getAvailability` and `isSlotEmpty` take an `excludeId` so the booking being edited doesn't count against itself), and only emails the customer if `notifyCustomer` isn't `false`.
- **Incomplete bookings are allowed on the dashboard** (`POST /bookings/admin-add`): names, email, phone and party size may be missing. Anything that renders or emails a booking must cope with that: skip the customer email when there is no address, and use `save({ validateBeforeSave: false })` when saving them. The public route (`/bookings/add`) requires everything.
- **Charters** (`charter: 'true'`) block their trip by existing as an active booking. Nothing writes to the `Availability` capacity rows for charters any more. (Older charters did; that data is in the old database, which the new one replaced, see P1-10.)
- **Charter payments:** the booking is created by `fulfillCheckoutSession` in `controllers/charters.js`. It is called by both the Stripe webhook (`POST /charters/webhook`, mounted in `index.js` *before* `express.json()` because it needs the raw body) and the `/success` page, and is idempotent through the unique `stripeSessionId` on the booking. Only the call that creates the booking sends the emails. Keep it that way: don't create charter bookings anywhere else.
- **Save first, email after.** Once a booking change is saved, send emails with `trySend` (it reports failure and never throws), and say so in the response if one failed. Never let a failed email undo, hide or turn a saved change into an error. `sendEmail` throws, so only use it where no change has been saved yet.
- **HTML emails must use the `safeHtml` tag** (`utils/safeHtml.js`): write `html: safeHtml\`...${value}...\`` and every `${value}` is escaped, because customers type the names and messages that go into emails. Never build email HTML with a plain template literal or string concatenation. Plain-text emails (`text:`) don't need it.
- **Emails are real.** Add, update, cancel, restore and charter all send through Gmail. In tests, mock nodemailer (see below). Update and cancel always email the owner address too.

## Backups (Atlas free tier has none)

- `npm run backup` saves every collection of the sandbox database to `backups/<database>-<date>/` (one JSON file per collection, exact types). `npm run backup -- --production` reads the live database with `atlasDB_user_prod`, `atlasDB_user_prod_password` (and `atlasDB_name_prod`, default `Test`) from `.env`; it only reads. The files hold customer details and `backups/` is git-ignored: never commit them. **Take one before any risky change** (the P1-10 date migration, cleanup scripts) and remind the owner to take one regularly.
- `npm run restore -- ../backups/<folder>` (a dry run) and `... --apply` add back documents missing from the **sandbox** (matched by `_id`; it never edits or deletes). It refuses to run anywhere else. Restoring into the live database is deliberately manual.

## Auth

- Login `POST /admin/login` (rate limited to 5 per 15 min per IP) returns an 8-hour JWT. The client keeps it in `localStorage` under `adminToken` and sends `Authorization: Bearer ...`.
- **Public routes:** `POST /bookings/add`, `POST /bookings/monthAvailability`, `GET /admin/getSeasonDates`, `/charters/*`. **Everything else must use `requireAuth`**, including any new dashboard route.
- **Security headers and CORS live in `middleware/security.js`.** The Content Security Policy only allows the site itself, Google Fonts and the Vimeo player: **adding any outside service (a script, map, analytics, image host, frame) means adding it to the policy there**, or the browser silently blocks it. `CSP_REPORT_ONLY=true` turns the policy into log-only if a deploy breaks something. In production no CORS headers are sent at all (the site and API are the same site); `CORS_ORIGINS` (comma separated) lets other sites in, and outside production any local page is allowed. Never put `upgrade-insecure-requests` back in outside production.
- **Public routes are rate limited** (`middleware/rateLimiters.js`: per IP, plus per email for bookings; in memory, so they reset on restart) and the booking and charter-checkout routes have a **honeypot** (`middleware/honeypot.js`, hidden form field `website_url`). Any new public route that sends email or calls Stripe needs a limiter, and any new public booking form must include the honeypot field. Customer input goes through `utils/validateBooking.js`. The Stripe webhook is deliberately not limited.
- **Wrap every route handler in `asyncHandler`** (`middleware/asyncHandler.js`) when adding routes. Express 4 doesn't catch async errors, and an uncaught one used to crash the server. Errors then reach `middleware/errorHandler.js`, the last middleware in `index.js`, which returns a generic JSON error. Controllers can still catch errors themselves to give a specific message.
- On the client, use `authAxios` (from `services.jsx/auth.jsx`) for protected calls and plain `axios` for public ones. A 401 clears the token and logs the dashboard out.

## Front-end conventions

- Match the file you are in: client code is 4-space indented, JSX, no PropTypes, `.jsx` for components. Server controllers are mostly 4 spaces, a few files use 2.
- Dashboard CSS is scoped under `.dashboard`. Be careful with global CSS: `bookingForm.css` has bare `form div`, `form button`, `form select` and `form textarea` rules that apply to every form on every page, and `dashboard.css` keeps a global `input` rule other forms rely on.
- The site navbar is absolutely positioned (4rem, 5rem for the mobile burger), so pages need top padding to clear it.
- A visually hidden element (`.sr-only`) inside a scrolling container needs a `position: relative` ancestor, or it widens the page.
- `BookingForm` serves the public page, the charter page and the dashboard. New behaviour for one must not change the others: it takes optional `booking`, `onResult`, `onDone` props that only the dashboard passes.

## Tests and checks

- **Run `npm run check` before calling any change done.** It runs lint (`npm run lint`), the server tests (`npm test`, about 10 seconds) and the browser tests (`npm run test:e2e`, about 40 seconds). Each can be run alone. CI (`.github/workflows/ci.yml`) runs the same steps on every push, with the same Node version as Heroku.
- **Every change gets a test, and a bug fix gets a test that fails without the fix.** Then check the test can fail: break the code on purpose, watch it go red, restore it. This is how the login that accepted lists as passwords was found, and how the "`.env` loaded too late" bug was guarded. If a test passes with your change sabotaged, the test is wrong.
- **Server tests** (`server/test/*.test.js`, Node's built-in test runner plus supertest): `validation` (pure rules, fixed clocks), `auth`, `bookings-public` (customer bookings and seat counting), `bookings-admin` (dashboard add, find, edit, cancel, restore, delete), `emails` (failed emails and escaping), `notes-season`, `charters` and `charters-off` (Stripe checkout, webhook, success page), `security-*` (headers and CORS in each mode), `rate-limits`, `startup` (runs the real `index.js` with only a `.env`), `scripts`.
- **How a server test file is set up, in this order:** `t.setEnv()`, `t.installMocks()`, then `require('../app')` (settings are read when the app loads), then `before(() => t.startDb())`. `helpers.js` gives each file its own settings, a fake mailer (`mocks.mails`, `mocks.mailMode` = `none|client|admin|all` to make emails fail), a fake Stripe (`mocks.stripe`; the real library still checks webhook signatures) and a throwaway in-memory MongoDB seeded with a season. Anything that needs a different environment (production, only a live key, `CORS_ORIGINS`, `CSP_REPORT_ONLY`) goes in its own file, because settings are read once per process. Tests never read `.env`, use a real key, or touch a real database.
- **Dates and visitors:** use `t.day(n)` for dates (customer bookings must be in the future and inside the season). Rate limits are per visitor, so pass `ip` (or let `t.call` invent one) to pose as different people.
- **`app.js` builds the app; `index.js` reads `.env`, connects and listens.** `.env` must be loaded before anything else in `index.js` (settings are read at load time). `startup.test.js` guards this.
- **Browser tests** (`e2e/*.spec.js`, Playwright): the real website, built like production in a temporary copy (`e2e/build-client.js`, so the tracked `client/dist` is never touched), served by `e2e/server.js` (the real app plus the same fakes, and a few `/__test` routes that live outside the app). Tests share one login (`h.logIn`) because the login form only allows 5 attempts per 15 minutes. **Known problems are written as `test.fail()` tests in `known-issues.spec.js`** (now: pages other than home don't hydrate cleanly, spec P2-9). When one starts passing, Playwright reports it, so delete its marker.
- **Dates and devices:** `calendar-devices.spec.js` checks the calendar blocks out-of-season days on desktop Chrome, an emulated Android phone (Pixel 7), and **WebKit** (the engine in iPhone, iPad and Mac Safari), each in three time zones (London, Los Angeles, Auckland). It exists because Safari once ignored the season dates, and it found a second bug: a season date read as UTC midnight (`new Date('2026-05-01')`) opens the day *before* the season for visitors west of London. **Never build a date from text on the client** (`new Date('2026-05-01')`, `new Date('2026-05-01 00:00')`, `new Date('01-05-2026')`): use the numbers (`client/src/utils/dates.js`: `parseDay` for YYYY-MM-DD, `toDay` to turn a Date into one). WebKit is the same engine as Safari but not a real iPhone, so a real phone check is still worth doing before go-live. On a new Linux machine WebKit needs `sudo npx playwright install-deps webkit` once.
- **The test database:** `mongodb-memory-server` downloads a MongoDB program once (`npm test` does this first via `server/test/prepare.js`; `MONGOMS_DOWNLOAD_DIR` chooses where; CI caches it). Many files starting databases at the same instant can pick the same port, so `startDb` retries and `npm test` runs at most 4 files at once. If a whole file ever fails at its first test with "port already in use", that's this.
- **What the tests can't prove:** a real paid Stripe checkout, the Vimeo video actually playing (Vimeo blocks automated browsers), real email delivery, and `eval()` blocking (the browser tool bypasses it, so the header is checked instead). Say so honestly rather than claiming they were verified.
- **Live checks are rare.** Anything against the real sandbox database or real Stripe test mode is a one-off: tag records `ZZTEST`, clean up, never use the live key, never write to production. The owner often has their own servers on 4040 and 5173 running: don't kill them, use other ports.

## Before moving the sandbox to production

**When the owner says they are moving this sandbox to production, remind them of this checklist before doing anything else.**

0. **All checks green:** `npm run check` passes locally and CI is green on the exact commit being deployed.
1. **Stripe webhook** (until it is set up, charters still work through the `/success` page, but a customer who pays and closes the tab gets no booking):
   1. Stripe dashboard → Developers → Webhooks → Add endpoint. Make sure the Test/Live toggle matches the key the server uses (`STRIPEKEY`).
   2. Endpoint URL: `https://www.sarkboattrips.com/charters/webhook` (the same address as `PUBLIC_URL`, plus `/charters/webhook`).
   3. Events: `checkout.session.completed`, and ideally `checkout.session.async_payment_succeeded`.
   4. Copy the signing secret (`whsec_...`) and run `heroku config:set STRIPE_WEBHOOK_SECRET=whsec_...`. Locally, put it in `server/.env` and use `stripe listen --forward-to localhost:4040/charters/webhook`, which prints its own secret.
   5. After deploying, use "Send test webhook". It should show a 200 reply (the sample event has no charter details, so it creates no booking).
2. **Heroku config vars** (the server exits at startup if the first three are missing): `admin_username`, `admin_password_hash` (make it with `node server/scripts/hash-password.js`), `JWT_SECRET` (long and random, e.g. `node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"`), `STRIPE_WEBHOOK_SECRET`, plus the existing `atlasDB_name` (**the new production database (see 7), not `Test` and not `Bookings-Sandbox`**) and either `atlasDB_password` (old shared user) or, once the `production-app` user exists (readWrite on `Test` only), `atlasDB_user=production-app` + `atlasDB_user_password` (then delete the old shared user in Atlas; **on Heroku the variables must be named `atlasDB_user` and `atlasDB_user_password`**, not the `_prod` names the laptop's `.env` uses), `gmail_address`, `gmail_password`, `STRIPEKEY` (live key), **`PUBLIC_URL=https://www.sarkboattrips.com`** and **`PRICE_ID`** (the live price that was typed into the code until now: `price_1QzL9TBMZ6qJyKg9hrBauqD6`; the `PRICE_ID` in the local `.env` is a different, unverified one). Check `heroku config:get NODE_ENV` prints `production` (Heroku sets it; if it isn't, charter payments switch themselves off rather than use the live key). Do **not** set `STRIPETESTKEY` on Heroku.
3. ~~`client/config.js`~~ Nothing to switch any more (see P1-6 in the spec). Just make sure the build runs: Heroku runs `npm run build` through `heroku-postbuild`.
4. **Deploy client and server together.** The dashboard now calls `/bookings/cancel`, `/restore` and `/permanently-delete`, and `/bookings/delete` no longer exists, so an old client with a new server (or the reverse) will break cancelling.
5. **Production data:** nothing is migrated (see 7: a new empty database). The first start creates a unique index on `bookings.stripeSessionId` (harmless). The season-dates document does not exist yet in the new database: set it in the dashboard (see 7).
6. **After deploying:** open the home page with the browser's developer console open and look for messages mentioning "Content Security Policy" (a blocked font, image or video). **Play the Vimeo video once** (it can't be tested automatically). If something important is blocked and you can't fix it quickly, set `CSP_REPORT_ONLY=true` on Heroku to stop blocking while you fix `middleware/security.js`. Leave `CORS_ORIGINS` unset. Then log in to the dashboard, check the season dates, make and cancel a test booking, and (if possible) run one small real charter payment and confirm the booking, the emails and the webhook delivery in Stripe.
7. **A brand-new database (P1-10).** The new code stores dates as `YYYY-MM-DD` and cannot read the old `Test` database, whose dates are `dd-mm-yyyy`. So go live on a **new, empty database** and keep `Test` untouched as an archive (it can still be browsed in Atlas). Steps: pick a name (Atlas creates it on first write), give the `production-app` user `readWrite` on it (Database Access, edit the user; it currently covers `Test` only), set `atlasDB_name` on Heroku to the new name, deploy, then **log in and set the season dates** (the new database has none, so the public site says "Bookings aren't open yet" until you do). Run `npm run backup -- --production` against the old `Test` first if you want a local copy.
8. Anything in `spec.md` marked DONE only counts once it is deployed.

## If the app ever moves off Heroku

The code has no Heroku address in it. On the new host: (1) run `npm run build` as the build command and `npm start` to run it; (2) set every setting in `server/.env.example`, and set **`NODE_ENV=production`** yourself (Heroku does it for you, and the HTTPS redirect and live Stripe key both rely on it); (3) set `TRUST_PROXY` to the number of proxies in front of the app if it isn't 1, and make sure the proxy passes `X-Forwarded-Proto` (the HTTPS redirect depends on it); (4) add the new host's address to the Atlas allowed list; (5) point `PUBLIC_URL`, DNS and the Stripe webhook endpoint at the new address; (6) rate-limit counters are in memory, so they aren't shared if you run more than one copy; (7) some hosts block outgoing mail ports, which Gmail SMTP needs (another reason for spec P2-10).
