# CLAUDE.md

Sark Boat Trips: booking site and owner dashboard for a small boat-trip business. MERN stack (React 19 + Vite client, Express 4 + Mongoose server, MongoDB Atlas, Stripe for saving and charging customers' cards, Zoho SMTP for email from info@sarkboattrips.com). Single owner uses the dashboard. This repo is the **sandbox** (`version2` branch, sandbox DB `Bookings-Sandbox`); production is the Heroku app from `main`. The payments work (card saved at booking, charged at the trip time) was merged into `version2` on 30 Oct 2026.

The backlog is in `spec.md`. Update it when an item is done or a new problem turns up.

## Run, lint, build

- Dependencies: server deps are in the **root** `package.json` (no `server/package.json`); client deps in `client/package.json`.
- **Local site:** two terminals, both from the project root: `npm run dev:server` (the API on 4040, restarts itself when a server file changes, uses Node's built-in `--watch` so `nodemon` isn't needed) and `npm run dev:client` (the website on 5173). Open `http://127.0.0.1:5173`.
- **Node:** use 22.11.0 (`nvm use 22.11.0`, the version Heroku and CI use). If a terminal says `npm` or `node` isn't found, nvm has no default: `nvm alias default 22.11.0`.
- **Server:** `cd server && node index.js` (default port 4040). dotenv reads `.env` from the *current directory*, so it must be started from `server/`. Heroku runs `node server/index.js` with config vars instead. No auto-reload: restart after server changes.
- **Client:** `cd client && npm run dev` (Vite, port 5173).
- **API URL:** nothing is hand-edited. `client/config.js` reads `VITE_API_URL`: `npm run dev` gets the local server from the committed `client/.env.development`, and a production build leaves it empty, so the browser calls the same site that served the page (the Express server serves both). Restart `npm run dev` after changing that file.
- **Lint:** `npm run lint` from the root (website code only). It must show 0 errors; the 7 warnings are fine. Build output (`dist`, `dist-server`) is ignored, and the project doesn't use PropTypes, so that rule is off.
- **All checks:** `npm run check` (lint, server tests, browser tests). See "Tests and checks".
- **Build:** `npm run build` rewrites the *tracked* `client/dist` and `dist-server`. Don't run it in place. For a build check use `npx vite build --outDir <scratch dir>`. If dist gets modified by accident, `git checkout -- client/dist` and delete the new hashed files.
- Never print `.env` values. `server/.env.example` lists every setting with comments. The names are: `PORT, admin_username, admin_password_hash, JWT_SECRET, atlasDB_name, atlasDB_user, atlasDB_user_password, atlasDB_password`, the email settings `MAIL_FROM` (every email comes from it, and customers are told to write to it), `OWNER_EMAIL` (where the owner's alerts go, default `MAIL_FROM`), `SMTP_HOST`, `SMTP_PORT` (465 or 587), `SMTP_USER` (default `MAIL_FROM`), `SMTP_PASSWORD` (without `SMTP_HOST` it falls back to Gmail with the old `gmail_address`/`gmail_password`), plus the Stripe and address settings: `PUBLIC_URL` (the site's public address, e.g. `http://localhost:5173` on a laptop and `https://www.sarkboattrips.com` in production; Stripe sends customers back to it and owner emails link to its `/dashboard`), `STRIPEKEY` (live; production only), `STRIPETESTKEY` (test; used everywhere that isn't production), `STRIPE_WEBHOOK_SECRET` (the `whsec_...` of that environment's webhook; without it `/charters/webhook` returns 503 and `/success` still creates the booking), optional `TRUST_PROXY` (number of proxies in front of the app, default 1), and an unused `DB_*` Postgres block. **Online booking only runs when `utils/settings.js` is satisfied** (every customer booking saves a card with Stripe, so without Stripe customers can't book online; dashboard bookings still work): outside production only a test key is used (a live key with no test key switches it off, so a laptop can never charge a real card), and a missing or invalid `PUBLIC_URL` switches it off with a clear message at startup and a 503 to customers. It is also refused (503) until the prices are set on the dashboard. There is no `PRICE_ID` any more: amounts come from the dashboard prices. Never type an address, price or key choice into the code: add a setting. The server exits at startup if `JWT_SECRET`, `admin_username` or `admin_password_hash` is missing. **Database:** `utils/database.js` builds the Atlas address (`atlasDB_user` + `atlasDB_user_password`, falling back to the original user `morganguille` + `atlasDB_password` until production has its own user). Outside production the server and the scripts refuse any `atlasDB_name` without "sandbox" in it; `MONGODB_URI` is the deliberate override. One Atlas cluster holds the sandbox database `Bookings-Sandbox` and the live site's `Test`; never touch `Test`.

## Layout

- `server/app.js`: the Express app (middleware and routes). Order matters: security headers, HTTPS redirect (production only), Stripe webhook (raw body, before `express.json()`), JSON, CORS, `robots.txt` and `sitemap.xml`, static `client/dist` (or `CLIENT_DIST`), routes, the pages router, error handler. **Pages (P2-9):** `client/prerender.js` builds each public page (`/`, `/bookings`, `/charters`, `/terms`, `/privacy`) to its own file with its own title and description (`dist/index.html`, `dist/pages/<name>.html`) plus `dist/app.html`, the empty page marked noindex; `server/routes/pages.js` sends each address its own file, `app.html` for the pages built in the browser (dashboard, success, canceled, manage), and `app.html` with a 404 status for anything else. A new public page goes in both lists (`PAGES` in prerender.js, `PUBLIC_PAGES` in pages.js; the sitemap comes from the second); a new browser-only page in `BROWSER_PAGES`, or it answers 404. Give every public page a `<title>` and `<meta name="description">`. `robots.txt` and `sitemap.xml` are made from `PUBLIC_URL`. `server/index.js`: reads `.env` first, checks the login settings, connects to MongoDB (`MONGODB_URI` overrides the Atlas address) and listens.
- `server/test/` (server tests and their helpers), `e2e/` (browser tests; `booking-form.spec.js` is the customer form), `.github/workflows/ci.yml` (CI).
- `server/routes|controllers|models|middleware`: `bookings`, `admin` (login, season dates), `charters` (routes only: Stripe checkout lives in `controllers/checkout.js`), `notes`. `server/emails/`: every email (see Emails). `middleware/requireAuth.js` checks the JWT. `scripts/hash-password.js` makes the bcrypt hash for `admin_password_hash`; `scripts/backup.js` and `restore.js` (see Backups). Money, dates and the report live in `utils/prices.js`, `utils/dates.js` and `utils/report.js`.
- `client/src/views` (pages), `components` (shared), `components/dashboard` (dashboard pieces), `hooks/useSeasonDates.js`, `services.jsx/` (API helpers, `auth.jsx` holds the token and `authAxios`), `utils/dates.js`, `css/`.

## Data and rules to remember

- **Dates** are `YYYY-MM-DD` text (for example `2027-05-01`) in bookings, availability and notes, in the database and over the API (season dates too: stored as UTC midnight, sent as `YYYY-MM-DD`). That form sorts and compares correctly as plain text, so "from today" and "this month" are simple searches, and it has no time zone. **People read it day-month-year (`dd-mm-yyyy`), so convert only where a person reads it:** `showDay` in `server/utils/dates.js` for dashboard messages and the report, `longDay` ("Monday 9 November 2026") and `shortDay` ("Mon 9 Nov", for subject lines) for emails, where a written-out month can't be misread by foreign visitors, and `showDay`/`prettyDate` in `client/src/utils/dates.js` for screens. `dayNumber`/`isDay` (server) check a value is a real `YYYY-MM-DD` day, and every route that takes a date refuses anything else (including the old `dd-mm-yyyy`). Never write a raw date into an email or message: use `longDay`/`shortDay` in emails, `showDay` elsewhere. The edit form uses `<input type="date">`, which gives `YYYY-MM-DD` and shows the visitor's own format.
- **Prices and the monthly report:** the owner sets the adult, child and charter prices in the dashboard's top row (`components/pricesForm.jsx`, `POST /admin/setPrices`; the public `GET /admin/getPrices` feeds the booking page, which has no price typed into it). They are stored **in pence** on the same single settings document as the season dates (that document can exist with only prices, so anything reading the season must check for missing dates). Infants are free. **Every booking saves the prices in force when it was made** (`booking.prices`), set only by the server in `addBooking`, `adminAddBooking` and `fulfillCheckoutSession`: a customer can never send them (nor `charter`, `status` or Stripe fields; `addBooking` takes a fixed list of fields). `utils/prices.js` (`bookingValue`: a charter earns the flat price, everyone else adults and children at their own prices) and `utils/report.js` (the monthly sums and CSV) hold the rules; don't work out money anywhere else. The report (`GET /bookings/report/:month`, `?format=csv` for the download) skips cancelled bookings, counts charter passengers inside adults and children (as the owner's spreadsheet does) and counts each charter once. Dashboard tab: Report. **The season dates and prices are locked (shown as plain text) until the owner presses Edit in the top bar**, to stop accidental changes; Done locks them again and drops unsaved typing. Tests must press Edit first (`editSettings` in `e2e/dashboard.spec.js`).
- **Collections:** the model named `Admin` is the `admins` collection and holds the single season-dates document. Don't rename it: production uses it. Model `bookings` is the `bookings` collection.
- **Cancellation rules (owner's decision, 30 Oct 2026):** free up to **24 hours** before a trip and **48 hours** before a charter; later, or a no-show, is charged in full; fewer people than booked are charged for the booking as made unless they told us before the deadline. Customers can cancel themselves up to the deadline from their manage-my-booking link (P2-6); after it, only the owner can cancel (not charged) or leave it (charged at the trip time). The numbers live in `server/utils/policy.js` (`cancelRule`, used by Stripe's page text and the confirmation emails) and `client/src/utils/policy.js` (the booking form, booking and charter pages, success page and the terms): keep both, and the terms, the same. The terms are `components/terms.jsx` and the privacy policy `components/privacyPolicy.jsx`, each on its own page, `/terms` and `/privacy`, linked from the footer (the addresses saved in Stripe's public details). `STRIPE_TERMS_CONSENT=true` makes Stripe's page ask customers to tick "I agree to the terms": only switch it on after the terms address is saved in the Stripe dashboard, or Stripe refuses every booking (checked: it does).
- **Party sizes:** adults (15 and over), children (4 to 14) and **infants (3 and under, free)**, each 0 to 12 (adults 1 to 12 for customers). **Everyone takes a seat, infants included** (the boat's limit counts every person). `utils/party.js` holds `seatsFor` (seats a booking uses) and `partyText` ("1 adult, 2 children and 1 infant" for emails): use them, never add the numbers up by hand. Infants cost nothing (`bookingValue` only charges adults and children). The report and CSV have an Infants column, and Passengers includes them.
- **Trips and their times (P2-2, `trip-tools` branch):** every day has the usual two trips, whose names (`timeslot`) are `'11am'` and `'2pm'`, leaving from the Creux Harbour. **The owner can move one trip for one day** to another time (7am to 8pm) and/or to the Maseline Harbour (low tide): dashboard **Trip tools** tab (moving, messaging and cancelling a whole trip live there, not on the Bookings tab, to keep the bookings list clear; owner 1 Nov 2026), **Change trip details** (`components/dashboard/changeTripForm.jsx`, `POST /bookings/change-trip` in `controllers/trips.js`). The change lives on that trip's `Availability` row (`startTime` `'15:00'`, `harbour` `'maseline'`; removed when set back to the usual), next to its capacity. **Bookings keep their timeslot, which names the trip; the trip's actual time and harbour always come from `utils/trips.js`** (`getTrip`, `getTripsForDay`, `tripsFor`, `withTrips`; harbours and their map links are in `HARBOURS` there). Everything time- or place-dependent asks it: the card charge, the booking cutoff (`validatePublicBooking`), every email (`withTrip(booking)` before building one: emails read `booking.trip`), the calendar file, Stripe's page text, the success page, the booking page and calendar panel (public `GET /bookings/trips/:date`; the calendar panel and the dashboard table show a moved time like a departures board, the new time in bold orange with the usual one crossed out underneath (`.movedTime`, `.usualTime`), and the calendar panel leaves out the harbour, owner's choice: no room, and the harbours are 100m apart) and the dashboard (moved-trip banner, the table's Time column). Never show `booking.timeslot` to a person as the time. Everyone on a moved trip gets `tripChangedEmail` (new details, the owner's note, a calendar file that replaces the old entry), unless the owner untick "Email the customers"; the owner gets one summary. A trip that has started can't be moved; overlapping the other trip is allowed with a warning. The terms say customers who can't make a new time can cancel free. **Message everyone on a trip** (`components/dashboard/messageTripForm.jsx`, `POST /bookings/message-trip`): the owner's text (up to 1000 characters, each line a paragraph) to every non-cancelled booking on one trip, any day including past ones, as `tripMessageEmail` with their booking details underneath (no calendar file); the owner gets `tripMessageOwnerEmail`. Both trip actions send through `emailEveryone` in `controllers/trips.js`. **Extra trips** (dashboard tab Extra trips, `components/dashboard/addTripForm.jsx`, `POST /bookings/add-trip`, `/bookings/edit-trip` and `/bookings/remove-trip`): a one-off trip on one day with its own name, note, time, harbour, seats, length (`hours`) and adult and child prices (pence, `prices`), stored as an `Availability` row with `extra: true` and a made-up timeslot (`x` + 6 hex, e.g. `x3fa9c1`) that its bookings store, so seat counting works unchanged. `getTripsForDay` lists the usual trips and the extras in time order; `findTrip` says whether a timeslot runs that day (every route taking a timeslot checks it; `isTimeslot` only checks the shape). Each trip has `label` ('3pm', 'Swim trip (4:30pm)', for lists and short messages) and `named` ('3pm trip', 'Swim trip (4:30pm)', in sentences: never write `${label} trip`). New bookings on one save its prices through `pricesFor(trip, current)` in `utils/prices.js`; moving a booking onto or off an extra trip re-prices it (owner's choice), between usual trips it keeps its prices. Never a charter (refused online and on the dashboard; the charter page and its calendar leave extras out). **Editing** (Edit next to Delete, the same form filled in) changes any detail: a new price applies to every booking on it that isn't paid (`paid`, `paid_in_person`, `charging` keep theirs; owner's choice, 1 Nov 2026, the form warns how many first), a new time or harbour emails everyone on it through `tellAboutMove` (shared with `changeTrip`, with the same "email the customers" tick box), and fixing the name, note, length or seats emails nobody (fewer seats than booked is allowed, with a warning). Deleting refuses while anyone is booked; with only cancelled bookings the row gets `removed: true` (hidden, but those bookings still read right). The day view and search add `tripLabel` and `tripStart` to each booking; the month availability adds `extras: [{ timeslot, spaces }]` only on days that have some.
- **Timeslots** are `'11am'` and `'2pm'`. Default capacity is 12, which is also the most any trip can have (`MAX_CAPACITY` in `validateBooking.js`: the boat's legal limit, owner 1 Nov 2026; the Availability tab and extra trips refuse more, and there is deliberately no overbooking). All seat counting lives in `server/utils/availability.js`: seats left = capacity minus the seats (`seatsFor`: adults + children + infants) of non-cancelled bookings, or 0 if the trip has an active charter. `isSlotEmpty` (open and no bookings at all) is the rule for booking a charter. Don't copy this logic elsewhere. **Anything that adds people to a trip checks and saves inside `withTripLock(date, timeslot, fn)`** (same file; P2-12): online bookings, dashboard add, edit and restore do, so two people can't take the last seats at once. A new way of adding people to a trip must do the same.
- **Cancel a whole trip** (`POST /bookings/cancel-trip` with `date`, `timeslot`, `reason` `weather` or `other`; `components/dashboard/cancelTripForm.jsx` on the Trip tools tab): closes the trip first (capacity 0, so nobody books it meanwhile; reopened from the Availability tab), cancels every active booking on it (so no card is charged), emails each customer the cancellation email with an apology (`cancellationEmail(booking, apology)` in `controllers/bookings.js`, shared with the single cancel), and sends the owner one summary: who wasn't emailed, and anyone who had already paid and needs a refund. The box is deliberately not a `<form>` (see the global form CSS below).
- **Reminder email** (`utils/reminders.js`, `runDueReminders(now)`, started every minute by `index.js` through `startReminderTimer` once the database is connected, with or without Stripe; both timers use `utils/timer.js`): at 6pm Guernsey time (`REMINDER_HOUR`) the evening before, every non-cancelled booking for tomorrow with an email gets one, except bookings made after 6pm (their id's timestamp says when they were made). Once only through `reminderSentAt` (claimed in one database step before sending); a failed send is retried each minute up to `MAX_ATTEMPTS` (3, counted in `reminderAttempts`); nothing is sent after midnight. `updateBooking` clears both fields when the date changes. No payment line (owner's choice).
- **Manage my booking (P2-6, `manage-booking` branch):** every booking has `manageToken` (32 random characters, the key to `/manage/<token>`; never sent to anyone but the customer) and `reference` (`SBT-` + 6 easy-to-read characters, for phone calls; the dashboard shows it under the name and searches it), made in `utils/bookingCodes.js` by a `pre('save')` hook in the model, and for older bookings by `withTrips` (`ensureManageLinks` in `utils/manage.js`) before any email. Customer emails with a booking (confirmation, updated, reminder, trip moved, trip message) carry a **Manage your booking** button (`manageButton` in `emails/index.js`) and the reference. The page (`views/manageBooking.jsx`, `controllers/manage.js`) lets the customer, **up to the free-cancellation deadline** (`freeUntil`: 24 hours before a trip, 48 before a charter, from `FREE_CANCEL_HOURS`; until the trip starts if the owner moved its time, as the terms say), **cancel** or **change the party size** (more people need the seats, checked inside `withTripLock`; a charter up to 12; the price follows `booking.prices`). A different day or time is a **message** to the owner (`customerMessageOwnerEmail`, reply-to the customer), allowed any time. After the deadline, or once paid (`paid`, `paid_in_person`, `charging`), or cancelled, the page shows why and the contact details (`whatCanChange`). Owner's decisions, 1 Nov 2026: phone bookings get the link too; every change emails the owner (`cancelledOwnerEmail(b, { byCustomer: true })`, `updatedOwnerEmail(b, { change })`). Changes save in one database step that only works while the booking is active and unpaid, so they can't race the card charge. Rate limited per IP, messages also per booking. The page has `noindex`.
- **Cancel, not delete:** bookings have `status` (`active` or `cancelled`) and `cancelledAt`. A booking with no `status` counts as active. Day view, search and the upcoming list hide cancelled bookings unless `?includeCancelled=true`. **Dashboard lists (P2-3):** the Bookings tab switches between Day (the table with the buttons) and Upcoming (`GET /bookings/upcoming?days=7|14|30|all`, default 7); search (`GET /bookings/search?q=&from=&to=`: name, email, phone ignoring spaces/+44/leading 0, or reference, matched as plain text, never as a pattern) and Upcoming both show `components/dashboard/bookingsByDay.jsx`, grouped by day, whose Open day shows that day (the calendar follows through its `value` prop). Shared booking wording (payment labels, party, amount) is in `components/dashboard/bookingDetails.js`. Permanent delete only works on cancelled bookings.
- **Validation lives in `utils/validateBooking.js`:** `validatePublicBooking` (async; customer bookings and charter checkout: required fields, email, lengths, party size 1-12 adults and 0-12 children, trip time, real date, not past, 1 hour cutoff in `Europe/Guernsey` time, inside the season), `validateAdminBooking` (dashboard add and edit: lenient, only checks what is given, past dates allowed) and `validateAvailabilitySetting`. The trip times (`11am`, `2pm`), the 12 limit and the cutoff are constants at the top of that file. Never compare dates as strings: use `dayNumber`. Values must be real strings or numbers, never lists or objects.
- **Editing a booking** (`updateBooking`): a field that isn't sent is untouched, an empty text field clears it, date, trip time and booking type are never blanked, a blank adults box leaves the number alone and a blank children box means 0. It saves through the document with `validateBeforeSave: false` (the validators in `validateBooking.js` run first), refuses if the new date, trip or party size doesn't fit (`getAvailability` and `isSlotEmpty` take an `excludeId` so the booking being edited doesn't count against itself), and only emails the customer if `notifyCustomer` isn't `false`.
- **Incomplete bookings are allowed on the dashboard** (`POST /bookings/admin-add`): names, email, phone and party size may be missing. Anything that renders or emails a booking must cope with that: skip the customer email when there is no address, and use `save({ validateBeforeSave: false })` when saving them. The public route (`/bookings/add`) requires everything.
- **Charters** (`charter: 'true'`) block their trip by existing as an active booking. Nothing writes to the `Availability` capacity rows for charters any more. (Older charters did; that data is in the old database, which the new one replaced, see P1-10.)
- **Online booking (trips and charters):** `controllers/checkout.js`. `POST /bookings/checkout` (trips) and `POST /charters/create-checkout-session` (charters; the route, never the customer, decides which) check the booking, create a Stripe customer and send the customer to Stripe Checkout in **setup mode** (save a card, nothing charged; the page says what will be charged and when). The booking is created only by `fulfillCheckoutSession`, called by both the Stripe webhook (`POST /charters/webhook`, mounted in `app.js` *before* `express.json()` because it needs the raw body) and the `/success` page (`GET /charters/verify-payment`); it is idempotent through the unique `stripeSessionId`, and only the call that creates the booking sends the emails. Online bookings start as `paymentStatus: 'card_saved'` with `stripeCustomerId`, `stripePaymentMethodId` and `cardLabel`. If the trip filled up while the customer was on Stripe's page, the booking is saved as **cancelled** with a `paymentNote` (never overbooked, nothing charged), and both sides are emailed; restoring it later makes it chargeable. The booking travels through Stripe as metadata (`kind` plus the fields; the message is split into `message` and `message2` because Stripe allows 500 characters per value). Don't create online bookings anywhere else. The old instant `/bookings/add` and the £80 deposit are gone. Emails: see "Emails" below.
- **Save first, email after.** Once a booking change is saved, send emails with `trySend` (it reports failure and never throws), and say so in the response if one failed. Never let a failed email undo, hide or turn a saved change into an error. `sendEmail` throws, so only use it where no change has been saved yet.
- **Emails live in `server/emails/`**: `index.js` has every email's wording (customer: `confirmationEmail` (trips and charters, also sent on restore), `updatedEmail` (with the new price when the customer changed their party), `cancellationEmail`, `reminderEmail`, `tripFullEmail`; owner: `newBookingOwnerEmail`, `updatedOwnerEmail`, `cancelledOwnerEmail`, `customerMessageOwnerEmail`, `tripFullOwnerEmail`, `failedChargesEmail`, `tripCancelledOwnerEmail`), `layout.js` the one shared look (email-safe tables and inline styles, white card, blue header with the logo embedded as an inline attachment `cid:logo@sarkboattrips` from `emails/logo.png`, a details box, a dashboard button for the owner, the contact footer and phone number for customers) and the plain-text copy every email carries, `calendar.js` the "add to calendar" file attached to confirmations and changes (trip 2.5 hours, charter 3, `UID booking-<id>@<domain>` so a change replaces the entry). Controllers only decide when to send: write a new email as blocks in `emails/index.js`, never as HTML in a controller. Customer subjects are plain sentences (no capitals); owner subjects carry who, how many and when. Sending is `utils/mailer.js` (`sendEmail`, `trySend`).
- **HTML emails must use the `safeHtml` tag** (`utils/safeHtml.js`): write `html: safeHtml\`...${value}...\`` and every `${value}` is escaped, because customers type the names and messages that go into emails. Never build email HTML with a plain template literal or string concatenation. Plain-text emails (`text:`) don't need it.
- **Emails are real.** Add, update, cancel, restore and charter all send through the mail server in the settings (`utils/settings.js` `mail`; Zoho for `info@sarkboattrips.com`). **Never type an email address into the code:** server emails use `settings.mail.sender` (From), `settings.mail.owner` (owner alerts) and `settings.mail.from` (the contact address in the text); website pages use `CONTACT_EMAIL` from `client/src/utils/contact.js`. `email-settings.test.js` fails if the old Gmail address appears anywhere in the code. In tests, mock nodemailer (see below). Update and cancel always email the owner address too.

## Backups (Atlas free tier has none)

- `npm run backup` saves every collection of the sandbox database to `backups/<database>-<date>/` (one JSON file per collection, exact types). `npm run backup -- --production` reads the live database with `atlasDB_user_prod`, `atlasDB_user_prod_password` (and `atlasDB_name_prod`, default `Test`) from `.env`; it only reads. The files hold customer details and `backups/` is git-ignored: never commit them. **Take one before any risky change** (the P1-10 date migration, cleanup scripts) and remind the owner to take one regularly.
- `npm run restore -- ../backups/<folder>` (a dry run) and `... --apply` add back documents missing from the **sandbox** (matched by `_id`; it never edits or deletes). It refuses to run anywhere else. Restoring into the live database is deliberately manual.

## Auth

- Login `POST /admin/login` (rate limited to 5 per 15 min per IP) returns an 8-hour JWT. The client keeps it in `localStorage` under `adminToken` and sends `Authorization: Bearer ...`.
- **Public routes:** `POST /bookings/checkout`, `POST /bookings/monthAvailability`, `GET /bookings/trips/:date`, `GET /bookings/manage/:token` and `POST /bookings/manage/:token/cancel|party|message` (the link's code is the key), `GET /admin/getSeasonDates`, `GET /admin/getPrices`, `/charters/*`. **Everything else must use `requireAuth`**, including any new dashboard route.
- **Security headers and CORS live in `middleware/security.js`.** The Content Security Policy only allows the site itself, Google Fonts and the Vimeo player: **adding any outside service (a script, map, analytics, image host, frame) means adding it to the policy there**, or the browser silently blocks it. `CSP_REPORT_ONLY=true` turns the policy into log-only if a deploy breaks something. In production no CORS headers are sent at all (the site and API are the same site); `CORS_ORIGINS` (comma separated) lets other sites in, and outside production any local page is allowed. Never put `upgrade-insecure-requests` back in outside production.
- **Public routes are rate limited** (`middleware/rateLimiters.js`: per IP, plus per email for bookings; in memory, so they reset on restart) and the booking and charter-checkout routes have a **honeypot** (`middleware/honeypot.js`, hidden form field `website_url`). Any new public route that sends email or calls Stripe needs a limiter, and any new public booking form must include the honeypot field. Customer input goes through `utils/validateBooking.js`. The Stripe webhook is deliberately not limited.
- **Wrap every route handler in `asyncHandler`** (`middleware/asyncHandler.js`) when adding routes. Express 4 doesn't catch async errors, and an uncaught one used to crash the server. Errors then reach `middleware/errorHandler.js`, the last middleware in `index.js`, which returns a generic JSON error. Controllers can still catch errors themselves to give a specific message.
- On the client, use `authAxios` (from `services.jsx/auth.jsx`) for protected calls and plain `axios` for public ones. A 401 clears the token and logs the dashboard out.

## Tests and checks

- **Run `npm run check` before calling any change done.** It runs lint (`npm run lint`), the server tests (`npm test`, about 15 seconds) and the browser tests (`npm run test:e2e`, about 6 minutes: they run on Chrome, and the calendar and phone specs also on an Android phone and WebKit). Each can be run alone. CI (`.github/workflows/ci.yml`) runs the same steps on every push, with the same Node version as Heroku.
- **Every change gets a test, and a bug fix gets a test that fails without the fix.** Then check the test can fail: break the code on purpose, watch it go red, restore it. This is how the login that accepted lists as passwords was found, and how the "`.env` loaded too late" bug was guarded. If a test passes with your change sabotaged, the test is wrong.
- **Server tests** (`server/test/*.test.js`, Node's built-in test runner plus supertest): `validation` (pure rules, fixed clocks), `auth`, `bookings-public` (customer bookings and seat counting), `bookings-admin` (dashboard add, find, edit, cancel, restore, delete), `emails` (failed emails and escaping), `notes-season`, `checkout` (online booking for trips and charters: Stripe's card page, webhook, success page, a trip filling up meanwhile) and `charters-off` (no usable Stripe key), `payments` (payment status, Mark paid), `infants` (infants free but taking a seat, everywhere), `charges` (the charge at the trip time: when, once only, failures, Stripe unreachable), `checkout-terms` (the terms tick box setting), `cancel-trip` (cancelling a whole trip), `overbooking` (people taking the last seats at the same moment: never over the limit), `manage` (manage my booking: links, cancel, party size, messages, deadlines), `reminders` (the reminder email the evening before, fixed clock), `trips` (moving a trip's time and harbour for a day, and everything that follows it), `security-*` (headers and CORS in each mode), `rate-limits`, `startup` (runs the real `index.js` with only a `.env`), `database` (which database, and the sandbox-only guard), `email-settings` (where emails come from and go to, and no old address left in the code), `email-layout` (the shared look, plain-text copy, logo, calendar file, written-out dates), `dates` (YYYY-MM-DD rules and showing them day-month-year), `prices-report` (prices, saved prices, the monthly report and CSV), `backups` (backup then restore gives the same data), `pages` (which page each address gets, 404s, robots.txt and sitemap.xml), `search` (the dashboard's search and the upcoming list).
- **How a server test file is set up, in this order:** `t.setEnv()`, `t.installMocks()`, then `require('../app')` (settings are read when the app loads), then `before(() => t.startDb())`. `helpers.js` gives each file its own settings, a fake mailer (`mocks.mails`, `mocks.mailMode` = `none|client|admin|all` to make emails fail), a fake Stripe (`mocks.stripe`: sessions created, customers, saved cards; the real library still checks webhook signatures; `t.bookOnline(app, body)` makes a whole online booking: checkout, card saved, webhook; `t.cardSession(id, fields)` is a finished checkout for webhook tests) and a throwaway in-memory MongoDB seeded with a season. Anything that needs a different environment (production, only a live key, `CORS_ORIGINS`, `CSP_REPORT_ONLY`) goes in its own file, because settings are read once per process. Tests never read `.env`, use a real key, or touch a real database.
- **Dates and visitors:** use `t.day(n)` for dates (customer bookings must be in the future and inside the season). Rate limits are per visitor, so pass `ip` (or let `t.call` invent one) to pose as different people.
- **`app.js` builds the app; `index.js` reads `.env`, connects and listens.** `.env` must be loaded before anything else in `index.js` (settings are read at load time). `startup.test.js` guards this.
- **Browser tests** (`e2e/*.spec.js`, Playwright): the real website, built like production in a temporary copy (`e2e/build-client.js`, so the tracked `client/dist` is never touched), served by `e2e/server.js` (the real app plus the same fakes, and a few `/__test` routes that live outside the app). Tests share one login (`h.logIn`) because the login form only allows 5 attempts per 15 minutes. **Write a known problem as a `test.fail()` test** (none at the moment: the last ones, pages other than home not hydrating cleanly, were fixed by P2-9 and are now ordinary tests in `seo.spec.js`). When one starts passing, Playwright reports it, so delete its marker.
- **Payments plan:** `paymentsspec.md` (the owner's decisions: every online booking saves a card on Stripe's hosted page and is charged automatically at the trip's start time; weather cancellations are cancelled in the dashboard first, so nothing needs refunding). Built (merged into `version2` on 30 Oct 2026): steps 1, 2 and 3 are done. **Step 3, the charge:** `utils/charges.js` (`runDueCharges(now)`, started every minute by `index.js` through `startChargeTimer` once the database is connected and only with a usable Stripe key; never in `app.js`, so tests never run a timer). It charges bookings whose trip has started (`tripStartsAt(date, timeslot)` in `utils/validateBooking.js`, Guernsey time, also used by the booking cutoff: the one place to change when P2-2 lets a trip's time move), that are `card_saved` and not cancelled, catching up on any missed. Each is claimed first (`card_saved` to `charging` in one database step), then charged off-session with idempotency key `charge_booking_<id>` and `receipt_email`. Paid: `paid`, `amountPaid`, `stripePaymentIntentId`. Declined or the bank wants confirmation: `unpaid` with a plain `paymentNote`, never retried, and one owner email lists the failures. Stripe unreachable: stays `charging`, retried after 10 minutes with the same key, given up after 5 tries. A charge left half done is looked up by its payment id, not repeated. Amounts come from `bookingValue` at that moment. Tests: `charges.test.js` with a fixed clock; the fake Stripe's `mocks.stripe.cards[pm] = 'declined' | 'insufficient_funds' | 'authentication_required' | 'unreachable' | 'processing'`. Step 1 (each booking has `paymentStatus`: `unpaid` (also when missing), `card_saved`, `charging`, `paid`, `paid_in_person`; the day view and search add `amountDue` in pence; Mark paid and Undo paid, which change status in one database step that only succeeds from the expected status, so they can't race the card charge). Read it before touching Stripe or payment status. Payment fields are only ever set by the server: never by `/bookings/add` or by editing.
- **Dates and devices:** `calendar-devices.spec.js` checks the calendar blocks out-of-season days on desktop Chrome, an emulated Android phone (Pixel 7), and **WebKit** (the engine in iPhone, iPad and Mac Safari), each in three time zones (London, Los Angeles, Auckland). It exists because Safari once ignored the season dates, and it found a second bug: a season date read as UTC midnight (`new Date('2026-05-01')`) opens the day *before* the season for visitors west of London. **Never build a date from text on the client** (`new Date('2026-05-01')`, `new Date('2026-05-01 00:00')`, `new Date('01-05-2026')`): use the numbers (`client/src/utils/dates.js`: `parseDay` for YYYY-MM-DD, `toDay` to turn a Date into one). - **The test database:** `mongodb-memory-server` downloads a MongoDB program once (`npm test` does this first via `server/test/prepare.js`; `MONGOMS_DOWNLOAD_DIR` chooses where; CI caches it). Many files starting databases at the same instant can pick the same port, so `startDb` retries and `npm test` runs at most 4 files at once. If a whole file ever fails at its first test with "port already in use", that's this.
- **What the tests can't prove:** a real paid Stripe checkout, the Vimeo video actually playing, and at what volume (Vimeo blocks automated browsers; `public.spec.js` stands in for Vimeo and checks only what is asked for, and when), real email delivery, and `eval()` blocking (the browser tool bypasses it, so the header is checked instead). ## If the app ever moves off Heroku

The code has no Heroku address in it. On the new host: (1) run `npm run build` as the build command and `npm start` to run it; (2) set every setting in `server/.env.example`, and set **`NODE_ENV=production`** yourself (Heroku does it for you, and the HTTPS redirect and live Stripe key both rely on it); (3) set `TRUST_PROXY` to the number of proxies in front of the app if it isn't 1, and make sure the proxy passes `X-Forwarded-Proto` (the HTTPS redirect depends on it); (4) add the new host's address to the Atlas allowed list; (5) point `PUBLIC_URL`, DNS and the Stripe webhook endpoint at the new address; (6) rate-limit counters and the per-trip booking lock (`withTripLock`) are in memory, so they aren't shared if you run more than one copy (more than one copy would need a database-level guard against overbooking); (7) some hosts block outgoing mail ports, which Gmail SMTP needs (another reason for spec P2-10).
